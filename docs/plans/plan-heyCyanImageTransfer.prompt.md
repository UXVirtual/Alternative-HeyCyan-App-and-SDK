## Plan: Unattended HeyCyan Image Transfer Validation

Build a debug-only, ADB-driven harness that triggers ten fresh captures on the paired glasses. For each capture, it will validate the BLE thumbnail **without repairing a damaged transfer**, retrieve the newly associated source JPEG over Wi‑Fi Direct, and measure capture-to-validated-original time. A run passes only if all ten iterations pass without intervention. File association is inferential unless the glasses expose a capture identifier.

**Important transport distinction:** The HeyCyan image path found in this repository uses the vendor **BLE SDK** for thumbnails and Wi‑Fi Direct HTTP for originals. No HeyCyan Bluetooth Classic image endpoint is documented. The plan will verify that boundary, not call BLE “Classic” or invent an RFCOMM protocol.

**Steps**

1. **Gate implementation on a hardware contract.** Record the phone, glasses firmware, permissions, and raw callback traces from more than one fresh capture. Verify whether the first `getPictureThumbnails` callback value is a packet index, its starting value and wrap behavior, how duplicates and the completion callback are numbered, whether a total/last index is available, and whether payloads have a documented or repeatably observed prefix/trailer. Do not assume `isComplete` proves that no packet is missing: establish a contiguous-range completeness rule with a verified first and last index, or stop and investigate if the SDK does not expose enough evidence to establish it. Also verify on hardware that `media.config` can be read in transfer mode, that exit-transfer plus confirmed P2P teardown restores camera readiness, and that capture/photo-ready/thumbnail retrieval works after that transition. Fail preflight on missing pairing, permissions, Wi‑Fi, ADB, or a competing glasses session—never wait for a prompt mid-run.
2. **Replace permissive thumbnail repair with strict, shared assembly.** Build a bounded, session-isolated assembler keyed by the *verified* packet index rather than callback arrival order. Accept a duplicate index only if its payload is byte-identical; fail on gaps, conflicting duplicates, late/out-of-session callbacks, missing completion, unexpected prefix/trailer, excess bytes, or timeout. Concatenate each verified payload **once**, in index order. Do **not** search for a later SOI, strip arbitrary leading junk, delete repeated blocks by content, merge overlapping bytes, or truncate at the first EOI to manufacture a decodable JPEG. Permit removal of framing bytes only when their exact format and length have been verified on hardware; otherwise fail and retain the raw evidence. Check the JPEG's expected boundaries and marker/segment structure, require a *full* decode (not just bounds or a successful preview), and verify thumbnail dimensions. A decodable image with a packet/framing/structure violation is a **failure**, not a repaired success. JPEG decoding cannot detect every entropy-bit error; if the glasses provide no CRC/checksum, report that residual limitation rather than claiming bit-perfect thumbnail integrity. Keep the old reconstruction helper, if useful, **diagnostic-only**, never in the pass path. Apply the strict path to the harness and reconcile production thumbnail consumers separately so they do not retain arrival-order assembly or silently accept a repaired image. Unit-test reordered callbacks, identical/conflicting duplicates, missing first/middle/last packets, late callbacks, malformed/truncated JPEGs, extra bytes, oversized transfers, and JPEGs that decode despite a missing or altered packet.
3. **Build one isolated capture-and-transfer state machine.** Hold one exclusive `GlassesSessionCoordinator` lease for baseline, capture, HTTP retrieval, and asynchronous cleanup; prevent other app listeners, background commands, auto-capture, or an official-app session from consuming the photo-ready event or singleton SDK/P2P slots. For each iteration: enter transfer mode, read a bounded baseline `media.config` filename set, exit transfer mode, and confirm P2P group removal **and** camera readiness before sending another command. Register the photo-ready listener before sending the capture command; require a successful command response and a fresh 0x02 photo-ready event before requesting and strictly validating the thumbnail. Re-enter transfer mode using existing P2P discovery, BLE-reported glasses IP, network routing, and HTTP paths; poll a bounded time for **exactly one** new JPEG in the manifest relative to the baseline. Record the baseline, event, delta, and selected filename; fail on unchanged names, multiple candidates, or ambiguous external captures, rather than selecting the latest filename. Require a complete HTTP 200 body, bounded size, full JPEG decode and 1920×1080 dimensions; fetch that same file with an independent second GET and compare byte counts and SHA‑256 hashes. Where hardware behavior permits, compare decoded thumbnail and original scene/orientation to flag gross mismatches, with a threshold calibrated on genuine captures rather than treating pixel equality as expected. Exit transfer mode, confirm group removal and network unbinding, then release the lease **only after** cleanup. If a thumbnail request times out and the SDK response slot may remain live, quarantine that slot/lease until a confirmed safe reset or BLE reconnect; never start the next iteration on an unproven clean state. Fail the run if cleanup cannot be confirmed.
4. **Automate and measure.** Add a host runner that builds focused tests and debug APKs, installs them without clearing pairing, streams ADB logs, launches only the targeted instrumentation test, and collects per-capture evidence. Run **ten consecutive fresh captures** with no taps, Tasker assistance, or manual capture steps. Use the phone's monotonic clock from immediately before the capture command through full first-download read, hash, decode, and dimension check; record repeat-download and teardown durations separately. Report every latency and the arithmetic mean only for a genuine 10/10 run; any failed or skipped iteration makes the whole run fail.

**Relevant files**
- `android/CyanBridge/app/src/main/java/com/fersaiyan/cyanbridge/ai/live/GeminiLiveGlassesImageCapture.kt` and `MainActivity.kt` — currently number some thumbnail fragments by callback arrival; `MainActivity.kt` also contains the P2P/HTTP patterns to reuse.
- `android/CyanBridge/app/src/main/java/com/fersaiyan/cyanbridge/plugins/walkingaid/WalkingAidImageCapture.kt` and `media/autocapture/AutoLoopVisualNoteGenerator.kt` — other thumbnail consumers; audit their framing, validation, callback isolation, and timeout behavior.
- `android/CyanBridge/app/src/main/java/com/fersaiyan/cyanbridge/glasses/GlassesSessionCoordinator.kt` — exclusive ownership across capture and asynchronous teardown.
- `android/CyanBridge/app/src/main/java/com/fersaiyan/cyanbridge/ui/wifi/p2p/WifiP2pManagerSingleton.kt` — existing P2P controller; avoid changing its state machine unnecessarily.
- `android/CyanBridge/app/src/androidTest/java/com/fersaiyan/cyanbridge/hil/` and `tools/hil/` — new hardware test and ADB runner.

**Verification**
1. Confirm the callback/framing and transfer-mode contract on physical hardware before changing production assembly. Run focused JVM tests and build both debug APKs.
2. Run the harness against the explicit physical ADB serial while collecting direct logcat evidence for ten distinct capture-command/photo-ready/thumbnail sequences, ten unambiguous new filenames, and ten completed teardowns. Do not count skipped tests or a generic instrumentation `OK` without ten iteration records.
3. Accept `10/10` only when every thumbnail passes strict packet/framing/JPEG checks **without heuristic repair** and every newly associated 1080p original passes complete download, decode, and identical repeat-download hash checks. Publish the measured mean **only after** that hardware run.

**Decisions:** As clarified, “no manual steps” means zero intervention **per run** after one-time pairing and permission setup. Ten successes provide hardware evidence of reliability, not a statistical reliability guarantee. Strict packet/JPEG checks can reject known damage even when a JPEG decoder succeeds; without a glasses-supplied checksum or capture identifier, they cannot prove bit-perfect pre-transfer bytes or absolute thumbnail/original identity. No implementation or hardware result is claimed yet.
