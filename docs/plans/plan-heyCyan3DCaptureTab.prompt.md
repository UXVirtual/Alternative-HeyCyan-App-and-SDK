## Plan: HeyCyan 3D Capture Tab

Add a `3D Capture` bottom-tab destination that is visible only when HeyCyan is the selected profile. It will reuse the verified count-confirmed capture and Wi-Fi Direct full-resolution transfer paths, then display the downloaded JPEG in the tab.

**Steps**
1. Add `MODEL_CAPTURE` navigation, label it `3D Capture`, use the existing model icon, and centralize a filtered destination list. Hide the tab outside HeyCyan across the primary shell and activity-owned bottom bars. On compact devices, preserve the five-item `NavigationBar` limit by showing `Glasses`, `3D Capture`, `Chats`, `Media`, and `More`; `More` exposes `Plugins` and `Settings`. On expanded layouts, use the corresponding navigation suite treatment while retaining direct access to every destination. Route selection back to `MainActivity` with an initial-destination extra; validate the requested destination against the selected profile on both cold start and `onNewIntent`, falling back to `GLASSES` when it is unavailable.

2. Add `ModelCaptureUiState` with `IDLE`, `CAPTURING`, `SYNCING`, `READY`, and `FAILED` phases; a user-safe status/error detail; and an opaque final-image asset ID. Keep the app-managed filesystem path in the Android adapter/repository, not as a file URI consumed by shared Compose. The adapter resolves the asset ID to a platform-decoded image for rendering and verifies the backing file before restoring `READY`. Add `StartModelCapture`, `CancelModelCapture`, and an opaque operation ID. Only the active operation may mutate state; ignore stale BLE, P2P, HTTP, speech, and teardown callbacks. Clear the final asset ID when a new operation begins or any terminal failure occurs. On process recreation, restore a verified app-managed asset or fall back to `IDLE` rather than exposing a stale `READY` state.

3. Extract `StatusCard` from the Glasses dashboard into a reusable `GlassesStatusCard`. Create a `ModelCaptureScreen` that shows it, the capture button, status/error detail, an animated local camera/image illustration while syncing, the final JPEG after success, and a disabled `Process into 3D model` button only after success. Keep `ModelCaptureScreen` platform-neutral: it receives the decoded image (or a platform image-loader callback) from its host and performs no file-path parsing, URI construction, or Android `File` I/O in `commonMain`.

4. Extract a count-confirmed capture operation from `captureAndPreviewHeyCyanImage()` so its baseline count, `02 01 01` capture, readiness wait, and follow-up count confirmation can be reused without forcing BLE thumbnail preview. Preserve the existing preview behavior as one caller. The extracted operation must take exclusive ownership of the photo-ready notification and release it in every success, failure, cancellation, and timeout path. Capture the pre-capture media manifest or an equivalent remote-media snapshot before issuing `02 01 01`; the follow-up count alone only proves that a photo was saved, not which JPEG it is.

5. Handle `StartModelCapture` in `MainActivity` as a single, profile-pinned operation: reject duplicate starts, acquire the existing glasses session/command ownership, announce `I'm taking a picture`, perform the count-confirmed capture, and immediately start Wi-Fi Direct transfer after capture persistence is confirmed. A profile change away from HeyCyan cancels the active operation, clears its queued announcements, transitions it to `FAILED`, and begins the normal session/P2P cleanup. Do not block the profile change or gate terminal cleanup on the current profile; cleanup must complete against the initiating operation/session even if the app navigates away, backgrounds, or receives a replacement operation request.

6. Generalize the high-quality transfer contract with a distinct `MODEL_CAPTURE` purpose and model-capture request object rather than reusing the AI-only `IMAGE_QUESTION` request, dialog, cancellation, or completion paths. For the model-capture request, derive the remote JPEG from the post-capture manifest delta against the pre-capture snapshot; do not select the globally newest JPEG by filename. Download to a `.part` file in app-managed storage, verify it is nonempty and decodable, atomically promote it to the final file, and retain P2P binding until teardown finishes. Publish `READY` only from the successful teardown callback. Any failure, cancellation, stale callback, or teardown failure must delete partial/final operation files, clear stale UI state, release the session, and leave capture retryable. Do not save to Gallery or send the image to image AI.

7. Add a request-owned `ModelCaptureAnnouncementQueue` that is the sole owner of these two utterances across Android and OpenAI TTS. It must issue one utterance at a time, use unique operation-scoped utterance IDs, advance only from that utterance's terminal callback (`onDone` or `onError`), and release/cancel its player or native utterance when the operation is cancelled. Queue `Syncing the image` behind `I'm taking a picture`; do not use `QUEUE_FLUSH` or independent OpenAI `MediaPlayer` completion alone as serialization. Start transfer as soon as persistence is confirmed, without waiting for either announcement. The queue must ignore callbacks after cancellation and must not consume, flush, or drive state transitions for unrelated app speech.

8. Add shared navigation/state tests, Android Compose tests for all capture UI phases, routing/gating tests, and a physical HeyCyan device test covering capture, count increment, manifest-delta JPEG selection, sync, failure recovery, and disabled 3D processing. Verify compact HeyCyan navigation exposes exactly five primary destinations with `Plugins`/`Settings` reachable through `More`, while non-HeyCyan navigation preserves the existing primary destinations. Add pure reducer/state-machine tests for legal phase transitions and invariants: only the current operation can finish, `READY` requires a verified asset ID, no final asset survives a terminal failure, and cancellation is idempotent. Cover duplicate start, cancellation, profile switch, operation-ID mismatch/late callbacks, capture timeout, manifest mismatch, image validation failure, P2P teardown failure, missing asset on restoration, and retry after every terminal state. Add Android rendering tests for a valid decoded asset and a missing/undecodable asset fallback. Add instrumentation coverage proving transfer begins before the first announcement completes, the second announcement begins only after the first terminates, unrelated speech is not interrupted or treated as a capture callback, and profile change/background cancellation still releases the initiating session and tears down P2P.

**Decisions**
- Label: `3D Capture`.
- Visibility: hidden outside selected HeyCyan; remains visible while HeyCyan reconnects.
- Placeholder: local animated camera/image illustration.
- Final image: app-managed storage and in-tab display only.
- Image contract: the shared UI receives a decoded platform image or loader callback keyed by an opaque asset ID; Android-owned storage paths never cross the `commonMain` UI boundary.
- Capture identity: each request is pinned to one HeyCyan session, opaque operation ID, pre-capture media snapshot, and post-capture manifest delta.
- Completion ordering: `READY` is published only after image validation, atomic promotion, P2P teardown, and session release succeed.
- Profile change: leaving the HeyCyan profile cancels the active model-capture operation while its initiating session completes cleanup in the background.
- Announcements: a model-capture-owned queue serializes only its two status phrases; unrelated speech remains independent.
- Compact navigation: HeyCyan uses five primary destinations, with `Plugins` and `Settings` in `More` while `3D Capture` is available.
- Excluded: Gallery duplication, upload, and actual 3D-model processing.

Validation will run shared portability tests, focused instrumentation tests, `:app:assembleDebug`, and a physical-device transfer check using the established `DataDownload` and Wi-Fi P2P log tags.
