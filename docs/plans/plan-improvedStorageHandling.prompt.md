## Plan: HeyCyan Storage Handling

Implement a HeyCyan-specific media inventory, bounded capture transaction, and reliable complete-media sync. Capture success will be determined only by a pre/post `02 04` photo-count increase, not `errorCode`; thumbnail retrieval happens only after that success signal. Sync must account for photos, videos, and voice notes, expose a bounded failure rather than getting stuck, and verify its BLE/P2P/HTTP teardown before another glasses workflow can start.

**Steps**
1. Extend [GlassesDashboardPresentation.kt](../../android/CyanBridge/shared/src/commonMain/kotlin/com/fersaiyan/cyanbridge/shared/glasses/GlassesDashboardPresentation.kt) with typed media counts, scoped capacity state, and capture availability/result state. Keep inventory separate from transfer-progress counts.
2. Update [GlassesDashboardScreen.kt](../../android/CyanBridge/shared/src/commonMain/kotlin/com/fersaiyan/cyanbridge/shared/ui/glasses/GlassesDashboardScreen.kt) with a HeyCyan Glasses status section: `Photos`, `Videos`, `Audio`, scoped `Remaining media slots`, manual refresh, and a prominent `Sync images` action. Disable only Capture + Preview when blocked; sync remains enabled.
3. Extract the inline `02 04` callback in [MainActivity.kt](../../android/CyanBridge/app/src/main/java/com/fersaiyan/cyanbridge/MainActivity.kt) into a typed count-read operation which preserves `GlassesSessionCoordinator` command-slot behavior and stores successful counts in dashboard state.
4. Add profile evaluation for only `AM02_V1.2` / `AM02_1.20.00_260702`: $max(0, 4 - photos - videos - audio)$. All other hardware/firmware remains unknown. Invalidate this policy if five total items are later verified.
5. Replace the HeyCyan Capture + Preview path with a coordinator: baseline count, one existing capture command, bounded wait with ACK/notification diagnostics, follow-up count, then preview only when photo count increased. On no increase, set the current Storage full state, prompt Sync images, do not retry, and do not request a thumbnail.
6. Refactor [GeminiLiveGlassesImageCapture.kt](../../android/CyanBridge/app/src/main/java/com/fersaiyan/cyanbridge/ai/live/GeminiLiveGlassesImageCapture.kt) so thumbnail collection is only reachable after persistence has been confirmed. Do not promote its current packet/JPEG heuristics to a strict assembly implementation.
7. Rework the HeyCyan branch of media sync in [MainActivity.kt](../../android/CyanBridge/app/src/main/java/com/fersaiyan/cyanbridge/MainActivity.kt) into an explicit state machine around the existing `startDataDownload`, P2P callbacks, `showDownloadSuccess`, `showDownloadError`, and `teardownDownloadP2pSession` paths. Model and display the stages `preflight`, `entering transfer mode`, `waiting for P2P`, `waiting for glasses IP`, `reading media.config`, `downloading`, `verifying`, `exiting transfer mode`, `tearing down`, `completed`, and `failed` rather than leaving the UI at an indeterminate generic progress state.
8. Apply the harness gates from [HeyCyanImageContractProbeTest.kt](../../android/CyanBridge/app/src/androidTest/java/com/fersaiyan/cyanbridge/hil/HeyCyanImageContractProbeTest.kt) before each production sync: require connected and ready BLE, a quiet stable setup window, no active background vendor command, no existing P2P group, and no process-bound P2P network. Acquire a `MEDIA_SYNC` lease before entering transfer mode. On a command, P2P, IP, manifest, download, exit, or teardown timeout, stop the current attempt and retain/quarantine the lease until teardown is confirmed or a real BLE reconnect clears the vendor state. Do not layer an unbounded automatic retry over a stuck session.
9. Make manifest processing complete and type-aware. Parse the established `/files/media.config` over the P2P route, enumerate every supported image, video, and audio/voice-note entry, and create a durable per-item transfer ledger keyed by the exact remote filename and expected type. Count a file as complete only after its bounded HTTP download, local write, and gallery/import step succeed. Preserve a failed-item list with reason and byte count; do not report all media synced when any listed item remains untransferred. Treat an unavailable or malformed manifest as a bounded sync failure with exported diagnostics, never as an empty gallery.
10. Add bounded progress and cancellation semantics for the whole sync and each file: network/HTTP connect and read timeouts, byte/progress watchdogs, an aggregate deadline derived from manifest size/count, and cancellation that closes active HTTP work before P2P teardown. Keep the current official and custom flow choices, but make both report the same typed terminal result: complete, completed with failed files, cancelled, or failed before manifest. Retry only explicitly selected unresolved files in a fresh, preflighted session; do not re-download successful entries or issue another transfer-mode command while the prior session remains unconfirmed.
11. On each successful transfer completion, run a fresh `02 04` count only after the session lease and P2P teardown are confirmed. Record the before/after counts alongside the manifest totals and transfer result. Do not assume download removes source media; only a measured count change can clear the current storage-full result or re-enable Capture + Preview. Also refresh this status after reconnect, explicit refresh, and capture completion.

Expand [GlassesDashboardPresentation.kt](../../android/CyanBridge/shared/src/commonMain/kotlin/com/fersaiyan/cyanbridge/shared/glasses/GlassesDashboardPresentation.kt) and [GlassesDashboardScreen.kt](../../android/CyanBridge/shared/src/commonMain/kotlin/com/fersaiyan/cyanbridge/shared/ui/glasses/GlassesDashboardScreen.kt) with a separate sync summary: planned/completed/failed counts by Photos, Videos, and Audio, current stage, and an actionable retry-unresolved-files or Sync images command. Keep the storage inventory separate from transfer progress, ensure that a stopped sync cannot appear complete, and provide a direct way to exit a stuck visible state while background cleanup proceeds.
13. Persist redacted diagnostic evidence for every sync attempt: BLE setup sequence and device identity/firmware, transfer-mode ACK and glasses IP callback timestamps, P2P group/network transitions, exact `media.config` status and digest, type/file counts, per-file result/timing/byte count, teardown outcome, and before/after media counts. Follow the test harness export pattern in [run_heycyan_image_contract.sh](../../tools/hil/run_heycyan_image_contract.sh), without exporting raw private media or device-identifying addresses into user-visible logs.

Add fixture-based tests for a manifest containing mixed `.jpg`, `.mp4`, and `.opus` entries, partial failure, stalled P2P/IP/HTTP states, cancellation, teardown timeout, and reconnect recovery.

**Verification**
1. Run shared and Android JVM tests for capacity/profile, manifest parsing, per-file ledger behavior, sync timeouts, cancellation, teardown quarantine, and capture state transitions.
2. Run Compose tests for visible status, unknown capacity, disabled capture, enabled sync, refresh action, Storage full prompt, mixed-media progress, partial-transfer failure, and retry-unresolved-files state.
3. Build the debug app and use the physical-device HIL procedure as a bounded sync diagnostic: verify a stable BLE gate, transfer-mode transition, P2P group, BLE-reported glasses IP, `HTTP 200 /files/media.config`, at least one of each available media category, and confirmed P2P/process-route teardown. Re-run no workflow until the prior teardown is confirmed or a real reconnect occurs.
4. Confirm the final ledger accounts for every manifest item, including voice notes; a partial result must name the unresolved entries and never show success. Confirm a post-sync `02 04` read, rather than download completion alone, controls storage-full clearance and capture re-enablement.
5. Confirm a non-increasing capture count produces no thumbnail request or retry; confirm a physical transfer-stall exits visibly with retained diagnostics and does not leave the SDK/P2P session reusable without verified cleanup.

**Scope Decisions**
- HeyCyan only; no behavior changes for Eyevue, TuneBuds, Meta, or generic transfer UI.
- `errorCode`, including `FF FF`, remains diagnostic evidence only.
- No strict thumbnail packet assembly, guessed framing, or automatic capture retries.
- Media sync may not claim that source media was deleted or that glasses capacity was recovered without a fresh `02 04` observation.
- The HIL harness is the behavioral reference for lifecycle gates, evidence collection, and cleanup discipline; it is not a license to infer undocumented callback framing, manufacture a media endpoint, or promote observational transfer behavior into a protocol guarantee.
